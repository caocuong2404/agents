# Application contracts and invariants

Version: 1.1  
Date: 2026-11-02  
Purpose: implementation requirements supporting the ADRs, not an implemented SDK or public protocol standard. No runtime tests are reported.

Change classification: SUBSTANTIVE additions for Task transitions, fences, write idempotency and gate separation amend ADR-004, ADR-005, ADR-006, ADR-010 and ADR-012 with explicit change notes in those records; new identity and operational decisions are ADR-014 and ADR-015. Closed vocabularies, field definitions and vocabulary alignment are EDITORIAL unless explicitly identified in those amendment notes. All ten v1.0 required invariants below are retained verbatim. The immutable original is in provenance.

## Transport and identity

Use authenticated HTTP for adapters and MCP for compatible agent clients. Both call the same application services. Derive the effective principal and permitted workspace set from verified credentials and WorkspaceGrant records, as required by ADR-014. Reject unauthorized object IDs before reading content. Schema versions are explicit; reject incompatible versions with a structured error. Caller identity, role, source text and object references never supply authority. Check the object's stored workspace as well as the requested workspace.

No master credential, provider token, executable shell string or approval secret is included in a task/context payload. Record references identify data, not permissions. Policy is server-owned and read-only to models. An unavailable grant authority or an active kill switch denies new mutating work. Owner recovery and reconciliation retain only their explicitly scoped control permission.

## Core entities

“Active from Gate N” is the earliest permitted implementation stage, not a claim that a gate passed. Fields inherit their entity's gate unless stated otherwise. A later gate is additive; Gate 1 needs no Task, Assignment, Operation or Approval table, scheduler or model runtime. Gate 2 can use the existing harness as its only executor; Gate 3 qualifies a replaceable external executor. Inactive entity data must not be created to satisfy an earlier gate.

Approval is the single record vocabulary. An approval request creates a PENDING Approval; an approval decision updates that same Approval and its decision_receipt. There are no separate request/decision entity types. Pairing and webhook delivery verification at Gate 4 need not activate the Gate-5 Router Event store.

An operation proposal has no execution authority by itself. At dispatch, the broker binds the authorized operation to the current task epoch/generation and rechecks the immutable approval-bound intent. Reassignment cannot mint permission to rerun it. Source event keys deduplicate delivery. Source edits create a new event/version rather than overwriting the original observation. Trace/correlation IDs assist routing and diagnostics; they are not identity claims.

### Field dictionary

Every field below inherits its containing entity, call or fence gate. References are opaque identifiers resolved under current access control, not bearer capabilities. Optional means absent, never an implicit permission. All time values are server-checked UTC timestamps; durations remain policy choices where OPEN. IDs are opaque stable strings; revisions/generations are monotonically increasing integers within their stated authority, not wall clocks. The same field name has the same meaning in every entity; status uses the containing entity's closed enum. No client can supply a server-owned field to override authority.

## Initial application interface

Signatures are semantic contracts; concrete HTTP paths and language bindings belong to implementation. Snake-case names are canonical; earlier camelCase parameter spellings are editorially normalized, not separate fields. Every mutating call includes a fence and an idempotency key. Read calls still require current authentication and authorization. Named internal/control calls are not exposed as general model tools. Register new mutating routes here before enabling them.

| `approval.invalidate` (mutation)     | approval_id, reason, fence: RecordFence, idempotency_key                                  | Internal service expires/revokes under current policy; cannot approve.                                                                                                            | Active from Gate 4 |

The effective identity comes from server authentication, never these parameters. An executor role string cannot expand registered capabilities. The native harness uses the same claim/fence rules at Gate 2; Gate 3 adds external-executor replacement tests. Internal broker dispatch requires its own service-principal RecordFence and, separately, an execution_fence resolved for the current Assignment. The first authorizes the caller; the second is execution-context evidence binding the registered executor, Task revision/epoch/generation and live lease. The broker must not impersonate the executor to pass caller authentication, and an executor cannot use its token as a broker service credential. Neither broker credentials nor its service fence are handed to the model. A late outcome/reconciliation uses a current service RecordFence to preserve evidence without reviving the old executor or creating a new effect. It binds current Task authority and the Operation record_revision; historical dispatch epoch/generation remain receipt evidence and are not renewed execution grants.

For memory.remember, the server sets producer_ref and observation metadata from the verified source. It validates trust_class against origin; callers cannot promote learned content to SERVICE_RECORD or OWNER_INPUT. A replacement names the version-bound supersedes_ref in content and requires matching expected_revision; the server atomically marks the earlier record SUPERSEDED and creates the new CURRENT record. An exact retry returns the same new memory_id/revision. Classification is required and checked before retaining content.

memory.forget is initially a scoped reversible tombstone excluded from normal recall. Permanent erasure is an authenticated operator/retention operation covering artifacts, indexes and backups according to ADR-015; it is not an unrestricted agent tool. Approval creation/decisions, policy administration, secret access and privileged effect dispatch are not ordinary agent-exposed tools. Approval creation uses the broker-only approval.create transition, bound to the exact Operation; no model can create an APPROVED record.

### Fence protocol — Active from Gate 0

MutationFence is a closed union of ControlFence, ScopeFence, RecordFence and ExecutionFence. Tokens are opaque authenticated server handles; knowing an ID/epoch/generation tuple cannot mint one. All bind their verified principal, workspace/action/resource scope, authority_epoch, policy_version and credential_version. The parameter named fence must authorize the authenticated caller. The separate execution_fence on operation.dispatch is validated against the Assignment's executor principal and execution scope, in addition to the broker's own fence; it is not caller authentication. The current authority resolves and checks the handle on every mutation. Check authentication/access first, then current token validity (including epoch/generation/policy and ExecutionFence task revision/lease), then the idempotency lookup. An exact committed replay is a result read, not a new transition. Only a new request proceeds to expected-revision/state guards and atomic mutation. A fresh valid RecordFence may retrieve an older committed result even though that request's original expected_revision is now old; it cannot apply another mutation with that revision. Do not disclose current revisions or token contents to an unauthorized caller. An old idempotency record cannot bypass a stale fence.

| Fence type     | Additional binding and purpose                                                                                                                       | Activation         |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| ControlFence   | Current operator control revision and approved change scope; bootstrap is offline, not an unauthenticated API                                        | Active from Gate 0 |
| ScopeFence     | Current scope/catalog revision; admission/claim transaction compares current target revision/epoch/generation even though no prior Assignment exists | Active from Gate 1 |
| RecordFence    | Entity ID, record_revision or task_revision; Task-related records also bind authority_epoch and generation; permits only that actor's transition     | Active from Gate 1 |
| ExecutionFence | Assignment ID, executor principal, task_id, task_revision, authority_epoch, generation and live lease reference                                      | Active from Gate 2 |

executor.claim validates its ScopeFence, registration and current QUEUED Task in one authority transaction. Return a fresh ExecutionFence only with the committed Assignment. Heartbeat renewal extends the server lease record; it does not make an expired handle valid. Checkpoint, report and operation.propose require the same fence protocol; a retained connection is irrelevant. Steering, cancellation, reassignment, revocation, lease expiry, kill switch and restore invalidate affected handles. A claimant resuming after an idempotent claim replay gets the original result only if its Assignment is still current; otherwise return STALE_FENCE, never a silently renewed assignment.

Structured Error fields (Active from Gate 0): code (ErrorCode), message (safe text), call_name, retryable (boolean), reason (FenceReason when code is STALE_FENCE), recovery (RecoveryAction), and optional current task_revision/authority_epoch/generation visible only to an authorized caller. ErrorCode is the closed set AUTHN_REQUIRED, ACCESS_DENIED, INCOMPATIBLE_SCHEMA, STALE_FENCE, REVISION_CONFLICT, IDEMPOTENCY_CONFLICT, INVALID_STATE, INVALID_ARGUMENT, APPROVAL_REQUIRED, APPROVAL_EXPIRED, KILL_SWITCH_ACTIVE, RATE_LIMITED. FenceReason is the closed set EPOCH_MISMATCH, GENERATION_MISMATCH, REVISION_MISMATCH, LEASE_EXPIRED, ASSIGNMENT_CLOSED, CREDENTIAL_REVOKED, POLICY_CHANGED, SCOPE_MISMATCH. RecoveryAction is the closed set REFETCH_AND_REAUTHORIZE, CONTACT_OWNER, NONE. These code/reason/action values are Active from Gate 0. ScopeFence itself is first used at Gate 1.

An illustrative error body (not an observed runtime response) is {"code":"STALE_FENCE","call_name":"executor.checkpoint","reason":"GENERATION_MISMATCH","retryable":false,"recovery":"REFETCH_AND_REAUTHORIZE","message":"Execution authority is no longer current."}.

An authorized stale execution request returns HTTP 409, code STALE_FENCE, its call_name, a reason, retryable=false and recovery=REFETCH_AND_REAUTHORIZE. It changes no current state, lease, receipt, approval, operation or idempotency record. A redacted rejection log is diagnostic only. A revoked/unverified caller can receive AUTHN_REQUIRED or ACCESS_DENIED first; this must not reveal whether a forged object exists. Re-fetching authority is not permission to resubmit a write automatically. Epoch/generation/revision equality does not override an expired lease, changed policy or disabled principal.

### Idempotency — Active from Gate 0

Keys are opaque caller-minted stable request identifiers, persisted before retry. A new transport attempt reuses the original key. Canonical request arguments include all logical fields, immutable reference digests and expected revision; exclude transport metadata, the fence handle and retry timestamps. Canonical JSON uses deterministic object-key ordering and schema-normalized scalar representation. Different canonical arguments under one key return IDEMPOTENCY_CONFLICT without mutation. Same key/arguments return the original committed result after current authorization/fence checks; they never repeat a logical mutation.

| Call family                                    | Dedupe namespace                                                     | Rule                                                                                                                  | Activation                                            |
| ---------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| control.configure                              | principal_id + call_name + idempotency_key                           | One reviewed control change                                                                                           | Active from Gate 0                                    |
| memory.remember / memory.forget                | workspace_id + principal_id + call_name + idempotency_key            | Remember returns the same memory_id/revision; forget returns its tombstone result                                     | Active from Gate 1                                    |
| task.create and other non-operation mutations  | workspace_id + principal_id + call_name + idempotency_key            | One transition/result; server also enforces entity revision and guards                                                | Active from Gate 2, except recovery.restore at Gate 1 |
| operation.propose                              | workspace_id + task_id + task_revision + call_name + idempotency_key | Key survives executor replacement; trusted Task owner atomically stores descriptor, key and newly minted operation_id | Active from Gate 4                                    |
| operation.dispatch / recordOutcome / reconcile | operation_id + call_name + idempotency_key                           | A new transport key cannot bypass the Operation state/dispatch receipt                                                | Active from Gate 4                                    |

On proposal retry/replacement, recover the prior key/operation_id from durable task evidence; do not mint a new logical intent to escape an unresolved Operation. Distinct keys for identical or changed effect arguments do not automatically authorize a second action: the broker must resolve the earlier intent, and new intent requires current policy/approval. The operation_id is minted by the trusted Task owner, never by the executor or external provider. Use operation_id as the stable provider key where supported. No claim of exactly-once effects is made. Key/tombstone retention and maximum accepted retry/replay age are OD-04; do not erase dedupe evidence while a replay remains admissible. For control/recovery mutations the same canonical/conflict rule applies from Gate 0/1 respectively.

### Transition guards and actors — Active from Gate 2

Each row requires G plus the listed guard. G means verified actor/action/workspace grant, current policy/credential version, matching authority_epoch, generation and task_revision under the authoritative writer's compare-and-set transaction, a current MutationFence of the stated actor, and enabled policy. For creation, compare the ScopeFence catalog/workspace epoch and expected absence, then initialize the new record server-side. An owner control stop/recovery may use its explicit recovery permission while normal ingress is disabled. E adds a live current Assignment and its ExecutionFence. Q adds QUEUED state and atomic registration/capability/budget/lease admission under the claimant's ScopeFence. R adds an authorized owner/reviewer RecordFence and review of current evidence/criteria. Stage-inactive guards (e.g. Operations before Gate 4) are vacuous because those records cannot exist, not because a check is bypassed.

## Operation lifecycle

All OperationStatus values and transitions are Active from Gate 4. PROPOSED becomes AWAITING_APPROVAL, DENIED or, only for a policy-eligible Tier-0 application action, DISPATCH_PENDING. The allowed test mutation is treated as Tier 1 and requires approval. Operation authority_epoch/generation are dispatch bindings, distinct from the immutable approval descriptor. Before first dispatch only, the broker may bind the current Assignment after full intent/policy/approval revalidation. An IN_FLIGHT or UNKNOWN Operation cannot be rebound to authorize another write. A valid Approval does not immediately call a remote API: the broker records DISPATCH_PENDING, rechecks authority, then records IN_FLIGHT. AWAITING_APPROVAL becomes DENIED on rejection, CANCELLED on expiry/revocation/cancellation, or DISPATCH_PENDING with valid APPROVED exact intent. PROPOSED and DISPATCH_PENDING may also become CANCELLED before sending. IN_FLIGHT becomes SUCCEEDED, FAILED or UNKNOWN according to evidence. UNKNOWN becomes SUCCEEDED or FAILED only through scoped reconciliation; it cannot be blindly retried. A FAILED operation may return to DISPATCH_PENDING only after proof that no effect occurred, current fence/policy/approval checks and provider idempotency reconciliation; otherwise propose a separately authorized new intent. SUCCEEDED, DENIED and CANCELLED are terminal. Replay returns evidence without new dispatch. Every transition has the current broker/service fence, expected record revision, epoch/generation and dedupe guard from the call registry.

- Use the stable operation_id as the logical idempotency key across delivery retries.
- Reusing that ID with changed arguments is an error.
- A worker retry does not mint a new logical operation for an unresolved earlier intent.
- If the provider's idempotency retention window has passed, reconcile before attempting a write.
- An approval callback replay can return the existing decision but cannot dispatch again.
- UNKNOWN blocks blind retry and Task completion that depends on the action.
- A stop or expiry cannot retroactively cancel an already-performed remote action.
- External service policy/identity and application permission are checked on each relevant attempt.

| From               | To         | Trigger/actor                                               | Guard and consequence                                                                                                                                            |
| ------------------ | ---------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| absent             | PENDING    | Broker creates exact-intent Approval                        | Current Task/Operation RecordFence, expected record revision, current owner/workspace binding, descriptor_hash and expiry; idempotent approval.create transition |
| PENDING            | APPROVED   | Verified owner decision                                     | Current RecordFence, owner/channel binding, exact descriptor, current Task epoch/revision, unexpired approval and eligible Tier 1                                |
| PENDING            | REJECTED   | Verified owner decision                                     | Same authority/binding checks; no dispatch                                                                                                                       |
| PENDING, APPROVED  | EXPIRED    | Expiry service before first dispatch                        | Current service RecordFence and server time beyond expires_at; deny new write                                                                                    |
| PENDING, APPROVED  | REVOKED    | Owner/policy/credential/kill/restore or intent supersession | Current control/service fence; record reason; prohibit future dispatch                                                                                           |
| any existing value | same value | Matching decision/delivery replay                           | Current authority/fence and same canonical payload; return existing outcome; never dispatch again                                                                |

REJECTED, EXPIRED and REVOKED are terminal. An approved intent changed before dispatch becomes REVOKED, not silently edited. Replay and supersession have no extra enum values: replay is a no-op, supersession is a revocation reason. After first dispatch, consent is historical evidence; expiry does not erase it or undo an effect. Record a later revocation if needed, and permit read-only reconciliation, never a second write based on the old decision. The existing 15-minute approval expiry remains provisional; OD-09 is OPEN for overnight phone review. No new expiry value is selected.

## Budget reservations

The shared account/workspace budget ledger serializes concurrent reservations; independent per-task estimates do not enforce a combined ceiling. A Task stores its reservation reference. Reservation, task acceptance and remote inference are coordinated through idempotent intents, not a fictitious distributed transaction. Reconcile orphaned reservations, delayed provider usage and uncertain charges before releasing capacity. Apply both concurrency and per-request limits to bound possible overshoot. Existing provisional budgets remain in ADR-003; OD-10 requires owner calibration before paid use.

## Context construction

1. Resolve the Task under authenticated scope (Active from Gate 2).
2. Read current revision, criteria, relevant status and approved constraints from authority.
3. Select permitted evidence and learned memories within the requested budget.
4. Return provenance and references for omitted detail.
5. Record the context's Task revision and source record versions on the Assignment through a guarded assignment mutation.

Authorization configuration remains server-enforced and read-only to execution models. Retrieved text, even a memory labeled as a previous instruction, cannot grant a capability. Large logs or artifacts are fetched through authorized references rather than placed in every prompt. At Gate 1 clients use memory.recall/read with provenance; task-bound context.build is inactive. Context construction itself is a read; committing context_ref belongs to executor.claim/checkpoint with its fence and key.

## Export, restore and compatibility

Export a manifest with schema versions, scopes, task revisions, operation IDs/receipts, memory records, native-session references and artifact digests for active entity types only. Protect exports under the same classification and access policy as originals. Imports start inactive. Restore rotates authority_epoch, revokes old execution/approval grants and reconciles remote operations after the restore point. Rebuild projections from the selected authority. Do not claim native CLI processes or token caches were restored. ADR-014 defines the non-rollback authority/revocation root; ADR-015 defines backup options and owner configuration. No retained-data reliance until the applicable restore drill and OPEN prerequisites are resolved.

## Required invariants

1. One authoritative writer owns each task/operation record.
2. Only current epoch/generation and accepted revision can alter current execution state.
3. Event delivery and context membership do not grant authority.
4. Approval covers one exact operation intent and cannot be self-issued by an agent.
5. No required result depends solely on sandbox-local data after the task settles.
6. External ambiguity is represented and reconciled.
7. Search indexes and summaries never override current task or permission records.
8. An unavailable controller/approval channel does not grant additional execution rights.
9. A restored backup cannot reactivate stale workers or silently replay historical effects.
10. A device's real-time safety does not depend on cloud/model availability.
